What you get

The backend, not a box of parts.

Database + API

Your schema is the API

Create a table, get REST endpoints — filtering, ordering, pagination and relationship embedding included. It is PostgREST under the hood, so the query grammar is documented, stable and not ours to break.

  • PostgreSQL 17, no forks or dialects
  • Connection pooling on by default
  • Direct connection string for anything else
JAVASCRIPT
const { data, error } = await corebase
  .from('projects')
  .select('ref, status, created_at')
  .eq('status', 'READY')
  .order('created_at', { ascending: false })
  .limit(20)
Auth + row-level security

Authorisation lives next to your data

Email and password auth with rotating refresh tokens, wired into Postgres row-level security. Your access rules are policies in the database, not middleware you have to remember to apply.

  • Policies enforced by Postgres itself
  • New tables are locked by default, not open
  • OAuth and magic links on the roadmap
SQL
create policy "own rows only"
  on profiles for select
  using ( auth.uid() = user_id );

-- new tables are force-RLS by default:
-- no policy means no access, never accidental access
Storage + local dev

Files, and the whole stack on your laptop

S3-compatible object storage with the same policy model as your tables. And corebase dev runs the real components in Docker — the same Postgres, pooler and API you get in production.

  • Signed URLs, size and MIME limits
  • File permissions use the same RLS rules
  • Local and production paths are identical
