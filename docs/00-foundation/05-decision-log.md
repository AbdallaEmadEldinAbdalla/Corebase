# Decision Log

## Purpose

The single authoritative register of every locked decision in the corpus, ADR-style but compact. Any doc may *propose*; only entries here are *binding*. If two docs disagree, this log wins; if this log is silent, the disagreement is a bug — file it in [open questions](../15-risks/02-open-questions.md).

**Format:** `D-xxx — decision — rationale — where detailed`. Status is **Locked** unless marked *(provisional)*.

## Provisioning hardening (from M0/T5d, found by running it)

| ID | Decision | Detail |
|---|---|---|
| D-184 | Project containers are **created with no restart policy**; `wait_healthy` promotes them to `unless-stopped` only after the database answers `pg_isready` | A container that cannot initialise (bad config, corrupt volume, exhausted disk) flaps forever under `unless-stopped`, burning node CPU and hiding the failure behind a permanent `restarting` state — the health gate never sees a dead container to report. ## Crash recovery (from M0/T6, found by killing the worker)

| ID | Decision | Detail |
|---|---|---|
| D-193 | The stale-heartbeat threshold is **derived from the heartbeat interval** — three missed beats — and the runner refuses any threshold under two intervals | Chosen independently, the two drift into one of two failures. Too long and a crashed job's re-delivery arrives while the row still looks healthy: T6 measured BullMQ re-delivering at ~30s against a 90s threshold, the restarted worker declining the claim, BullMQ marking that delivery *complete*, and the project **never converging**. Too short and a live worker has a job stolen mid-step. Deriving one from the other makes the relationship un-driftable, and the constructor rejects a bad override rather than trusting the caller. [job queue & workers](../02-control-plane/04-job-queue-and-workers.md) |
| D-194 | Sweeper recovery deliveries carry their **own attempt-keyed job id** (`<key>#recover-<attempt>`), used only when the plain idempotency key is already occupied by a dead worker's delivery | Redis keeps the dead worker's job `active` with a live lock for the full `lockDuration` (60s) after the process is gone, so the sweeper can neither add under that key nor remove it — recovery took 60s when Postgres had known the worker was dead for 30. Keying by attempt makes repeated sweeps idempotent and a second crash distinct from the first. Safe **only** because the claim `UPDATE` in `provisioning_jobs` is the mutex: a stale delivery and a recovery delivery arriving together means one runs and one is skipped, never two runs. A row that was never delivered at all (the API died between COMMIT and enqueue) still gets the plain key — that is a first delivery, not a recovery. [job queue & workers](../02-control-plane/04-job-queue-and-workers.md) |
| D-195 | Every service log line carries an ISO `ts`, and every saga step logs its own duration | T6's 60s recovery mystery was read straight off these two fields; without them the finding would have been "sometimes recovery is slow". Also the raw material for T9's provisioning-duration histogram. [observability](../11-infrastructure/03-observability.md) |

## Deletion (from M0/T7)

| ID | Decision | Detail |
|---|---|---|
| D-196 | The purge is its own job type (`purge_project`), not a `mode` on `delete_project` | One row spanning both phases would share a single `checkpoint` set, a single `attempts` budget and one idempotency key across two operations a week apart — a purge that failed twice would inherit the soft delete's completed-step list and its exhausted retries. | D-197 | Delivery ids — and therefore the API's `Idempotency-Key` — must match `[A-Za-z0-9_.=#@-]{8,255}`; validated in the queue layer and rejected at the API boundary | The delivery id *is* the idempotency key (D-067) and BullMQ rejects `:` in job ids. | D-198 | Framework-level 4xx rejections keep their own status and message; only genuine faults become `500 INTERNAL` | Malformed JSON, an empty body under a JSON content-type, an unsupported media type, a payload over the limit — all arrived at the client as `500`, telling a caller who sent a bad request that our server was broken, and filling the server-error alert with other people's typos. Someone who wrote `0.5` or `200` did express an intent, so the honest response is the nearest bound rather than silently substituting 48; and a fleet that refuses to boot because of a typo is worse than one that keeps copies for a week and says so in its startup log. |
| D-294 | **The deadline is written in the same transaction as the restored project, and returned on the project *detail*, not only on the create response** | A nullable column filled in by a later step is a copy that lives forever whenever that step is skipped. And the customer who needs the deadline is the one coming back two days later, not the one who just pressed the button — a deadline visible only in the reply to a request already made is a deadline nobody can read, which is the same rule the soft-delete window follows (D-205). |
| D-295 | **A PITR target keeps its sub-second precision all the way to `recovery_target_time`** | The target was formatted by trimming the milliseconds off an ISO timestamp, which moves the requested instant backwards by up to a second. Not a rounding detail: a row committed at `11:23:16.5` is *before* a target of `11:23:16.819` and *after* the truncated `11:23:16.000`, so the restore returns a database that looks correct and is one transaction short — and a customer restoring to the second before a bad migration loses that second's writes with no way to tell. `recovery_target_time` accepts fractional seconds. Caught by the exit-criterion test's first execution of its data assertions, and pinned by a unit test that walks several millisecond values, because a single round-number case passes against the broken version. |
| D-296 | **`final_backup` is always a full, and a failure stops the deletion** | Everything else in the schedule balances cost against restore time; this is the only copy that will survive the project, and a chain whose earlier links are expiring is not something to hand a customer who is already having a bad day. Stopping the saga is the interlock: a deletion that proceeded past a failed final backup would close a recovery window with nothing behind it, and it would do so at the one moment nobody is watching, because the customer has already moved on. Nothing about a `DELETE` distinguishes "we are done with this" from "I typed the wrong ref". |
| D-297 | **Pause takes its backup *after* the checkpoint, confirms it with `pgbackrest check`, and refuses to stop the containers if either fails** | A paused project has no running Postgres, so WAL archiving stops with the container — unhandled, the only current copy of the data is one node's disk with a backup behind it that is already older than the pause. The order matters: a backup before the checkpoint omits exactly what the checkpoint flushed, which is the tail of the data. And `check` is what separates "we took a backup" from "the backup is in object storage", which are different claims and only the second one matters once the container is gone. Leaving the containers **running** on failure is the deliberate part: a paused project whose backup failed is strictly worse than a running one, which is the opposite of what pausing is for. |
| D-298 | **The pause backup is an incremental when the last full is under 7 days old, a full otherwise** | The chain matters more here than anywhere else because nothing will extend it again until the project resumes: an incremental onto a base that is about to become the oldest thing in the repo is a restore depending on a link nobody is watching. A project pausing before it has ever had a full therefore takes one — an incremental with no base is not a thing, which is what the first version of the test assumed. |
| D-299 | **`CB_REQUIRE_FINAL_BACKUP` defaults on** | Until P3f the flag could only make deletion *fail*, because there was no backup system for it to succeed with. It defaults on now because the failure it prevents is invisible: a recovery window with nothing behind it looks exactly like a recovery window, right up to the moment someone needs it. `=false` is the deliberate opt-out for a fleet with no object storage. |
| D-300 | **"Retrievable" is proven by reading the repo from a container that is not the deleted project's** | Exit criterion 4 promises the backup is retrievable during the recovery window, and a `backup_runs` row saying `succeeded` is our own bookkeeping. What has to be true is that the repo holds a restorable set reachable with the stored cipher-pass and nothing else, from anywhere the control plane can start a container — asking the deleted project's own container would prove nothing, since the point is that it no longer exists. |
| D-301 | **The control plane deletes purged repos itself, over S3, with a hand-written SigV4 client** | By the time a repo is due for destruction (purge + 30 days, D-066) the container, the volume, the placement row and the credentials are all gone — there is nowhere left to run `pgbackrest`. It is also the access model the design already asks for (backups §6): nodes put/get/list their own prefixes and **delete rights live only with the control plane**, so a compromised node can read its tenants' encrypted repos and cannot destroy history. Hand-written for the reason the Docker client is: the surface is a list and a delete, SigV4 is a specified stable algorithm, and an SDK wrapping all of S3 is a large supply-chain and upgrade cost for two operations. |
| D-302 | **`project_repos` outlives every other trace of a project** | The one thing that must survive a purge is the knowledge of what still needs deleting and when — the container, volume, placement row and secrets are all gone thirty days before the deadline. Until this table existed a purged project's repo simply stayed in object storage forever: the data a customer asked us to destroy, retained indefinitely, with nothing anywhere recording that it should not be. `ON DELETE RESTRICT` rather than CASCADE, because a future change that deleted the projects row would otherwise take the schedule with it and leave the objects behind, unreferenced. |
| D-303 | **Destruction is proven by re-listing the prefix, and the row is marked destroyed only when that list comes back empty** | Deleting and assuming is not destruction, and D-038 asks for *provable*. The same discipline as the purge's `verify_gone` against the node. A sweep that assumed would mark a repo destroyed while its objects remained — retained forever behind a row asserting they were gone, which is worse than not having tried. Failures keep the repo due so every sweep retries, and the stored `last_error` is what makes a repo that *cannot* be destroyed visible rather than merely retried in silence. |
| D-304 | **The repo path is stored, not derived, and the S3 prefix is the stored path with its leading slash removed** | It *is* derivable from the project id today, and a scheme change later would silently orphan every scheduled destruction — the row naming a path the code no longer computes, its objects missed by exactly the sweep meant to remove them. The slash matters for the same class of reason: pgBackRest spells the path `/projects/<id>` and S3 keys have no leading slash, so a list for the unmodified path matches nothing at all, silently — and the sweep would then "prove" an untouched prefix empty. |
| D-305 | **The control plane and the project containers reach object storage at *separate* configured endpoints** | In production both are R2 over the internet and the two are identical, which is why the control-plane pair falls back to the project pair. Locally they cannot be: a project container reaches the store through the data node's NAT egress, so its endpoint is an address on the compose network — and the control plane runs on the host, which cannot route to a container IP at all and must use the published port. Getting it wrong is a 30-second timeout indistinguishable from a wrong secret or a firewall, which is why it is two variables rather than one variable and a hope. |
| D-306 | **Every signed S3 request with a body sends an explicit `Content-Length`** | Node falls back to chunked transfer encoding without it and S3 rejects a chunked `DeleteObjects` outright — `411 MissingContentLength`. Signed along with the rest, which is the correct handling: the length is part of what the signature attests to. |
| D-307 | **Verification restores into a scratch container with its own volume, which never joins a project network and never publishes a port** | It exists to be read once and then destroyed. Joining a project's network or taking a port would make a copy of a customer's database reachable from somewhere, which is a tenant-isolation hole opened by the mechanism meant to protect them. It is also deliberately *not* labelled with `com.corebase.project.ref` — the reconciler keys on that label (D-235), and an unexpected container carrying it is drift. Both the container and the volume are removed in a `finally` on every path: a verifier leaking one of each per failure would fill the verification node exactly when the fleet is having its worst day. |
| D-308 | **Verification runs four checks, and the sanity count is the one that cannot be faked** | Recovery reaching consistency proves the restore finished. Data checksums prove the pages are not rotting — the reason `initdb --data-checksums` exists (D-269). `pg_amcheck` proves the indexes point at rows that are there, which a heap check cannot: the index is what queries actually read. And the sanity count compares against the *live* project's own catalogue, because a backup can pass every structural test and contain an empty database. The expectation is read from the live project before the scratch instance is touched — a comparison between two databases is meaningless if both sides came from the thing under test. |
| D-309 | **The sanity expectation uses `pg_class.reltuples`, not `count(*)`** | It runs against a customer's live production database and must not be a full scan of it. An estimate is the correct tool here: the check only needs to know which tables should not come back empty, and an approximate row count cannot turn a populated table into an empty one. |
| D-310 | **The verification queue puts never-verified projects first, and a failed verification does not count as one** | Ordering by longest-unverified gets the most important case exactly backwards: a project nobody has ever verified is the likeliest to be broken in a way nobody has noticed — a misconfigured repo, a cipher-pass that never matched, a schedule that never fired — and it has no timestamp to be old, so it sorts last. And D-176's rule that a failure treats the backups as nonexistent is expressed here as scheduling: the project stays at the front of the queue until a verification *passes*. |
| D-311 | **Two alerts, because a verifier that stopped looks exactly like a fleet whose backups are all fine** | `RestoreVerificationFailed` pages on any failure, at the same severity as a failed backup, because that is what it is. `RestoreVerificationCoverageLow` warns when the fraction of projects with a passing verification inside their plan's floor drops — the quieter and likelier failure, since nothing fires when nothing runs. The SLO is one number rather than an average of per-project ages: one project at 200 days is the whole story, and an average hides it. |
| D-312 | **The control plane's S3 client has no `PUT`** | Delete rights are the only write rights the control plane is supposed to hold (backups §6). The sabotage test needed to overwrite an object in a repo and does it with `mc`, from outside the product, rather than adding a `PUT` that would have quietly broken the access model the same phase documents. |
| D-313 | **Project end-user passwords use scrypt, not the argon2id named in D-111** | D-211 already made this trade for platform logins, and its reasoning applies with *more* force here: argon2id needs a native module — a compiled dependency in every image that touches a login — and this module absorbs **every project's** login load in one process (D-110), so the dependency would sit on the hottest auth path on the platform rather than on the control plane's. scrypt is memory-hard, has been in Node's standard library for years, and is on OWASP's acceptable list. D-111's other properties are kept: parameters live in the hash, and a weaker hash is upgraded on the next successful verify. **What this defers:** bcrypt verify-only compatibility for imported users, which D-111 promised so customers could migrate from GoTrue without a mass password reset — it needs a dependency of its own and nobody is migrating in yet. Recorded as a gap rather than dropped, because D-004's portability promise is supposed to cut both ways. |
| D-314 | **The `auth` schema's tables are created by the image at `initdb`, not by a saga step** | They are fleet-wide and identical for every project, and `initdb` is the one moment when no client can observe a half-created schema. It also means a project's users exist in the project's own database from its first second, which is what makes D-004's export promise true: `corebase export` carries users, sessions and identities out with a plain `pg_dump`, and nothing about a project's end-users is ever stored in the control plane. |
| D-315 | **`corebase_auth` is the only role with table privileges in the `auth` schema, and it gets its own password** | `service_role` is the one that makes this non-obvious: it is handed to a customer's server-side code and holds `BYPASSRLS`, so nothing about row-level security constrains it and the **only** thing between it and every end-user's password hash is the absence of a table grant. `developer` is excluded for the same reason — the customer owns their database and can grant themselves anything, but the default must not hand them their users' hashes in the connection string the dashboard displays. And the credential is not `authenticator`'s: the two have opposite privileges and opposite blast radii, so sharing one password would make a leak of the API's connection string a leak of every end-user's credentials. |
| D-316 | **No default privileges are altered for the `auth` schema, and the force-RLS trigger stays scoped to `public`** | The absent default grant is the fail-closed asymmetry D-108 chose for `public`, applied where it matters more: a table added to `auth` later is unreadable by the API roles until somebody says otherwise. And RLS must *not* be auto-enabled here — the trigger's `schema_name = 'public'` filter is load-bearing, because forcing RLS on `auth.users` would lock the auth module out of its own tables by a mechanism meant to protect customers' data, and the symptom would be every login on the platform failing at once. Both are pinned by tests, since both are properties of something *not* happening. |
| D-317 | **The data-plane auth API's error codes are lowercase and GoTrue-compatible, unlike every control-plane code** | The control plane's codes are ours to name; these are matched by client code — a supabase-js app branches on `error.code === 'invalid_credentials'` to decide between "wrong password" and "try again later". Renaming them to fit the house style would make every ported app's error handling fall through to its generic branch, which is the one failure mode a compatibility surface exists to prevent. The uniformity *within* the set matters more than the names: one code covers a wrong password, an unknown email and a banned user, because distinguishing them is an enumeration oracle. |
| D-318 | **Without a gateway, the auth module resolves the project from the signed `apikey`, not from the Host header** | D-051/D-110 have the gateway turn `<ref>.corebase.co` into a resolved project context, and there is no gateway before Phase 5. The `apikey` is a better substitute than a Host header rather than a worse one: a Host header is an unverified assertion the caller wrote, while the anon key arrives *signed by the project's own key*, so resolving it is one signature check rather than a lookup plus a trust decision. `apikey` is required on every endpoint anyway (D-029). What the gateway will add later is routing and rate-limit placement, not identity. The one exception is `/.well-known/jwks.json`, which is unauthenticated by design and so takes the ref from the Host subdomain or `?ref=` — it returns only public keys. |
| D-319 | **A project API key and an access token carry different `iss` values, and the auth module pins each separately** | The provisioning saga signs anon/service_role keys with the project's bare origin (`https://<ref>.corebase.co`), while the token spec gives an access token the auth module's own base URL (`.../auth/v1`). Pinning one string for both is not a simplification, it is a bug: the first live wiring of the module 401'd every request with a valid signature, because the issuer check was comparing an API key against an endpoint URL. |
| D-320 | **A user access token is refused in the `apikey` slot even though it is signed by the same project key and names the same ref** | A naive implementation accepts it, and it is the likeliest mistake a client will make. Letting a user's own token select the project is a different trust decision from a project key doing so: the key is published deliberately and carries a project-scoped role, while an access token is a *user's* credential and its `role` claim maps to a Postgres role. Accepting it would blur the two identities at the exact boundary where the module decides which database to open. |
| D-321 | **Per-project auth config lives in the control plane with column defaults standing in for a missing row, and `autoconfirm` defaults off** | D-110 puts the config in the control plane because there is one auth process and thousands of projects — it cannot hold per-project settings in its own configuration file. A missing row meaning "all defaults" is what lets every project created before the table existed serve auth correctly with no backfill. `autoconfirm` off is the one default here that is a security decision: on, anybody can create an account on somebody else's email address and use it, so it exists for local development against a Docker stack with no mail server and the dashboard warns while it is set. |
| D-322 | **A signup against a taken address spends a full scrypt hash it does not need, and the login path spends one when the email is unknown** | Both are pure waste in the mechanical sense and both are the endpoint's actual security content. Signup returns the same 200 and the same body shape with a decoy uuid whether or not the address exists; skipping the hash on the duplicate path would make that case answer in 2 ms and a fresh one in 100 ms, moving the enumeration oracle from the body into the clock. The same reasoning gives login a decoy verify for an unknown email. The cost is bounded by rate limiting the endpoint *before* the hash (D-241), which is what makes paying it affordable. |
| D-323 | **Each request to a project's auth endpoints opens its own connection to that project's database rather than using a pool** | A pooled connection holds a password; P2d rotation replaces it; every request served from that pool afterwards fails authentication until something notices and rebuilds it — and the symptom is *every login on a project breaking after a routine credential rotation*, in a subsystem the operator was not touching. The cost is a connect per request, milliseconds against a scrypt verify that is deliberately tens of them. Pooling is a change to make with a measurement in hand, and OQ-110 has to settle the pooler question first: the pooler's `auth_query` allowlists `developer` only (D-074), so routing auth through it changes the pooler's security posture and deserves its own step. |
| D-324 | **One-time tokens are consumed in a single UPDATE whose predicate includes `used_at IS NULL`, never select-then-update** | Two clicks on one link arrive concurrently more often than it sounds — mail clients prefetch, users double-click, corporate scanners follow every link — and a check-then-act lets both pass the check and both issue a session, which is precisely the replay that single-use exists to prevent. Proven by removing the predicate: two simultaneous verifies of one link both returned 200 and the database held two sessions. The predicate also excludes tokens belonging to soft-deleted users, so a tombstoned account cannot be confirmed back into a working session. |
| D-325 | **A `redirect_to` is validated where the link is *built*, not only where it is followed; and an unlisted value is replaced by `site_url` rather than rejected** | The first version of `/recover` passed `redirect_to` straight into the mailed link, which would have made Corebase send an attacker-chosen destination from its own reputable domain — the exact capability D-116's fixed templates exist to withhold. Replacement rather than rejection is deliberate: a mistyped redirect in a client must not turn a valid verification link into a dead one, while honouring it is the hole. The substitution is audited (`redirect_not_allowlisted`), because it is invisible to the developer whose redirect is being ignored and it is also what an exfiltration attempt looks like from our side. |
| D-326 | **A project with no `site_url` permits no redirect at all, and its `/verify` answers in JSON instead of guessing a destination** | "Configured nothing" must not read as "allowed everything", which is the direction an allowlist fails safely in. Inventing a destination for an unconfigured project would be the open redirect the allowlist exists to prevent, so the GET form degrades to the POST form's JSON body rather than picking somewhere plausible. |
| D-327 | **Session tokens ride in the URL *fragment* of a verification redirect, never the query string** | Same tokens, same URL, entirely different disclosure: a fragment is never sent to a server, so the tokens stay out of the destination's access logs, out of every proxy between here and there, and out of the `Referer` header. A query string would write a live session into somebody else's log retention. |
| D-328 | **Every successful `/verify` confirms the address, not just `type=signup`** | Clicking a recovery link proves control of the mailbox exactly as well as clicking a confirmation link does. Leaving an unconfirmed user unconfirmed after they have proved it sends them through a successful password reset into a login that refuses them for `email_not_confirmed` — a dead end reachable only by the people who most need the reset. |
| D-329 | **`/resend` replaces the outstanding token rather than issuing an additional one, and sends nothing at all to an already-confirmed or unknown address** | The `UNIQUE (user_id, token_type)` upsert means ten resends leave one live link in an inbox instead of ten; a user who clicks the first of five mails gets a dead link, which is the right trade against five simultaneously-valid credentials. Re-confirming a confirmed address is refused because it would otherwise be a way to make the shared sending domain deliver mail on demand to any address that happens to be registered (D-116). |
| D-330 | **The email pipeline's boundary is an `AuthMailer.enqueue` that cannot throw, and the delivery id is derived from the token, not from the queue** | An enumeration-safe flow has already committed to a same-shape 200, so a send failure that became a 500 would both break that contract and tell the caller their address was interesting. The delivery id is `<type>_<user id>`, which is the stable identity of "the link currently owed to this person" and therefore exactly the deduplication a delivery id is for. D-018's rule holds: the row of record is the `auth.one_time_tokens` row in the project's own database, so a Redis flush loses delivery and not the fact that mail is owed. |
| D-331 | **The `EmailProvider` interface ships with an SMTP implementation and no Postmark client; local and CI sending goes to a Mailpit container** | D-115's load-bearing half is the interface — "so cutting over is a config-and-warm-up project, not a rewrite" — and that is built. What is not built is a client for a paid API this project cannot exercise: a Postmark implementation with no account and no verified domain behind it is untested code on the one path where failure is silent and reaches users. SMTP is not a lesser substitute either: it is the same shape D-117's per-project custom SMTP needs, and Mailpit stands in for the provider exactly as MinIO stands in for R2 (a real listener, so our own protocol conversation, headers and MIME structure are what get exercised). What the substitute cannot exercise is deliverability — SPF, DKIM, DMARC and inbox placement are properties of a real domain at a real provider, and Phase 4's third exit criterion stays unmet rather than being declared met against a sink. |
| D-332 | **The SMTP client is hand-written, and sends one message per connection** | The same reasoning as the S3 SigV4 client and the JWT signer: what is needed is one narrow conversation, a general-purpose mailer brings a dependency tree and a plugin system for none of it, and every dependency has to survive `--experimental-strip-types`. One message per connection is slower and is the right trade for a queue-driven sender — a connection carrying one message cannot half-fail in a way that leaves the next message's state ambiguous, which is the failure mode that produces duplicate mail. |
| D-333 | **A display name is quoted, and both MIME parts are base64** | `Acme (via Corebase) <auth@…>` unquoted is **not** the name it looks like: parentheses delimit a comment in RFC 5322, so the recipient sees "Acme" alone — caught by the live sink, and it matters because the "via Corebase" half is what keeps us from claiming to *be* the customer while sending from our own domain, which is what DMARC alignment exists to catch. base64 for both parts removes the whole quoted-printable line-length and trailing-whitespace class of bug and makes dot-stuffing a formality rather than a correctness requirement. |
| D-334 | **Caps and suppression are checked at enqueue, not at send, and suppression is checked first** | Checking at enqueue refuses a burst while it is still one Redis round trip, instead of filling a queue whose drain rate is the thing the caps exist to protect. Suppression first because the reverse lets a mail-bomb against a suppressed address consume the project's whole hourly budget without one message being sent — the attacker gets to deny the project its legitimate mail for free. Counters are `INCR`-then-compare with a rollback on refusal: a `GET`-then-`INCR` lets two concurrent enqueues both read 29 against a cap of 30. An interrupted rollback under-sends slightly, which is the correct direction to be wrong in. |
| D-335 | **`email_sends` is the row of record for an owed email, and idempotency lives there rather than in the queue** | BullMQ deduplicates a duplicate *enqueue*; what actually produces duplicate mail is a worker that sends successfully and dies before recording it, after which the queue re-delivers and the provider has already accepted. So the row is checked before sending and updated immediately after. The window between those two is real and irreducible without provider-side idempotency keys — what it is not is *silent*, because `attempts` shows the retry. The table's other job is answering "why did my user get no mail", which a queue cannot: a queue's job is gone once it succeeds, and `suppressed` and `rate_limited` mean opposite things to a developer. |
| D-336 | **Retries are 30 s / 5 min / 30 min via a custom BullMQ backoff strategy, and a non-retryable failure is dead-lettered on the first attempt** | BullMQ's built-in `exponential` doubles from the base delay, which would give 30 s / 1 min / 2 min and exhaust the whole budget inside three minutes — shorter than the provider outage that is the only reason to retry at all. The retryable/permanent split is the other half: retrying a refused recipient or an unrenderable template three times over 35 minutes changes nothing and delays every mail behind it, while not retrying a connection reset drops a verification mail on a network blip. |
| D-337 | **Per-recipient counter keys are hashed, and the auth-email queue is separate from provisioning** | Redis keys appear in `MONITOR` output, slowlogs, memory dumps and any operator's `--scan`; a per-recipient counter keyed on the plaintext would put every end-user address of every project on the platform into all of them. The separate queue is an availability argument: provisioning jobs take minutes and hold a container's worth of state, sends take milliseconds and wait on a provider, so sharing one queue puts a provider outage's worth of retrying email in front of every project waiting to be created. |
| D-338 | **The grace-window replay issues a *replacement* child rather than returning the already-issued one, and revokes the child it replaces** | D-112 says to "return the already-issued child R′", and that is impossible as written: only `sha256(R′)` was kept, so R′'s plaintext cannot be handed to anyone a second time. Issuing a replacement under the same parent delivers the property the window exists for — a client whose response was lost gets a working token instead of a forced logout, and no second lineage is created. What differs is that the lost child's plaintext stops working, which is correct: the only party who might hold it is whoever received the response the retrying client did not. The replaced child is marked `revoked` rather than deleted, so a later family walk still sees the link existed. |
| D-339 | **The auth endpoints check session liveness on every bearer request; the data plane does not** | This is what makes `/logout` mean anything: an access token is stateless, so verifying it cannot reveal that the user signed out. Putting the same check on the data plane is the "strict mode" D-113 defers to V1.x — it adds a database round trip to the hot path D-051 exists to keep database-free and turns auth availability into data-API availability. The guarantee is therefore precisely stated rather than implied: on the auth endpoints revocation is immediate; on the data API refresh is dead immediately and access dies within `exp`. |
| D-340 | **A bearer token is rejected unless its `role` claim is `authenticated`, and its session must belong to the `sub` that presented it** | A project's anon and service_role keys are valid JWTs under the same keypair, so without the role check an API key works as a user credential. And the session lookup is keyed on `(session_id, user_id)` rather than `session_id` alone, so a token naming somebody else's session cannot operate on it — checking only the id would make correctness depend on `sub` being trustworthy in a place where it is the thing under test. |
| D-341 | **Session idle expiry is measured from `COALESCE(last_refreshed_at, created_at)`, and is per-project configurable with a one-hour floor** | Refresh tokens have no independent absolute expiry in V1, so this is the only bound on a lineage besides revocation — and treating a NULL `last_refreshed_at` as "never idle" would make a session that was never refreshed immortal, which is exactly the session belonging to a device nobody uses any more. The floor is an hour because below one access-token lifetime the setting stops being an idle timeout and becomes a mid-session logout: a client refreshing every 55 minutes would find its session already dead. |
| D-342 | **`?scope=global` builds its parameter list from its predicate** | Not a style point: `global` names no `$2`, and sending one anyway is a Postgres bind error — "bind message supplies 2 parameters, but prepared statement requires 1". It surfaced as a 500 from `?scope=global` while `local` and `others` worked, because those two reference the parameter. The test that should have caught it did not assert the logout's status, so the 500 passed as a successful global sign-out; an unchecked status on a mutation is a mutation that never has to happen. |
| D-343 | **The password-reset capability rides the reserved `amr` claim on the recovery-minted access token, not a flag on the session** | Flow 7 lets `PUT /user {password}` skip `current_password`, and Flow 8 requires it — so the two are distinguished by how the session was established. Marking the session would need a column in `auth.sessions`, which lives in the project-database image and has no per-project migration path (a gap in its own right). The claim table reserves `amr` for auth methods and states that adding claims is non-breaking, so this is the mechanism the doc already set aside. It also produces a *tighter* property than a session flag: the capability dies with the token that carried it — an hour at most, and deliberately not carried across a refresh — rather than lasting the session's thirty days. A recovery link is spent in seconds. |
| D-344 | **`PUT /user {email}` does not report that an address is taken; the collision is decided by the unique index at confirmation time** | Answering "that address is already in use" to a logged-in user turns this endpoint into exactly the enumeration oracle signup and `/recover` were carefully built to avoid, with one throwaway account and no effort. So the change is proposed either way and `applyEmailChange` distinguishes `23505` from a real error, returning a 409 to whoever confirms second. Two users genuinely can request the same address and both receive tokens; the index decides it and the loser is told rather than 500'd. |

The failure is silent in the worst way: reads return an empty list and writes affect zero rows *without error*, so a customer following the documentation installs a policy that appears correct and governs nothing. Same fix and same reasoning as the RLS cookbook's `SECURITY DEFINER` membership helper. The storage doc's three examples are corrected accordingly, and its pattern 3 gained the membership-read policy it had been missing for the identical reason. | P6a |
| D-393 | The `storage` metadata tables (`buckets`, `objects`, `upload_intents`) and the two helpers are owned by the project's `developer` role; the schema and `storage.usage` stay owned by the platform | Only a table's owner may create a policy on it, and policies on `storage.objects` *are* the file-permission system — every documented pattern is SQL a customer runs, and none of it is possible against a platform-owned table. The opposite call from the `auth` schema, deliberately: those tables hold password hashes no customer role may read, these hold the customer's own file inventory they are expected to govern. Costs the platform nothing, since the storage service connects as `service_role` and bypasses RLS by attribute. `storage.usage` is excluded because a customer who owned it could edit their way to unlimited quota, and the schema is excluded so it cannot be dropped from under the service. | P6a |
| D-394 | The storage service reads bucket enforcement config through `storage.bucket_config(name)` — SECURITY DEFINER — rather than as the caller | Size limits, the MIME allowlist and the `public` flag are platform enforcement inputs, not customer data: the service must read them to decide whether to accept bytes, and must read them for an *unauthenticated* request too, since a public-bucket GET has no caller identity and still needs to know the bucket is public. Reading them as the caller would refuse an upload whose *object* policy permits it merely because the *bucket* policy hid the row — a confusing failure with no good message. The leak is bounded and stated: existence and limits, to a caller who already had to know the bucket's name, where `bucket_id` (D-392) already leaks existence. | P6c |
| D-395 | Storage's routes are registered in two encapsulated Fastify scopes split by **body type** — JSON-bodied and byte-bodied — never by subject | Uploads carry opaque bytes of any content type, including `application/json` and `text/plain`, which Fastify parses by default; with those parsers in force a `.json` or `.txt` upload arrives as a parsed object or a string and the handler reports "send the object bytes as the request body". Overriding on one shared scope breaks the bucket routes' own JSON. Splitting by subject was tried and was still wrong: `POST /object/list` has a JSON body, so in the bytes scope its `prefix` read as `undefined` and the endpoint **silently listed the entire bucket** with no error. Neither parser may live on the root instance, where the gateway re-serialises `req.body` on its way upstream. | P6c |
| D-396 | Signed-URL tokens are a compact `base64url(payload).base64url(HMAC-SHA256)` format, deliberately **not** a JWT | A JWT carries its algorithm in the token, which is the root of every algorithm-substitution attack and the reason JWT verification is subtle to get right. These tokens have no header, no negotiation and one algorithm that is never named in the wire format, so it cannot be talked down. Nothing about a bearer capability in a URL benefits from being extensible. | P6d |
| D-397 | Signed-URL verification runs kid → signature → expiry → target, and refuses an unaccepted `kid` before deriving any key | The kid is the HKDF salt, so honouring an arbitrary one lets the attacker choose the key. Checking the target before the signature would answer questions about unsigned input; checking expiry first would tell a forger whether their fabricated `exp` was in the past. `verifyToken` takes the request's target rather than returning the payload, because a signature proves the token is ours while only that comparison proves it is for *this* object — ST-2 in the isolation matrix is a valid signature with the path swapped. | P6d |
| D-398 | The storage signing master secret is created **lazily on first use**, via `put`'s create-if-absent semantics, rather than at provisioning | Race-safe for a specific reason: `put` is `ON CONFLICT DO NOTHING`, so two requests racing to create it yield one secret — the first writer wins and the loser reads it back. `replace` would be the bug, invalidating every URL signed moments earlier. Lazy creation also means projects provisioned before this existed are not permanently unable to sign, needs no migration, and a project that never signs a URL never needs the secret. It is not a role password, so it does not belong in `store_credentials`. | P6d |
| D-399 | A redeemed signed URL and a public-bucket read are evaluated as `service_role`, with the permission decision made earlier | Neither has a caller to evaluate policies against: a signed URL is redeemed by someone who may not be able to authenticate, and a public object is fetched by anyone. Running RLS as nobody denies every one of them. So the question is asked earlier instead — at minting, under the requester's own policies (which is why minting checks visibility first, or the endpoint launders access), and at the moment a bucket is marked public, which is what "the bucket is the ACL" means. Every redeem failure returns one status and one message, because distinguishing expired from forged from wrong-object hands the holder of a bad token an oracle. | P6d |
| D-400 | A presigned upload's authorization is a **trial `INSERT` into `storage.objects` as the caller, rolled back in a savepoint** | The only way to ask Postgres whether this caller may create this row is to try: the customer's `WITH CHECK` can depend on the path, the bucket, their claims or a membership table, so there is no expression of the question that does not run their policy. The alternatives are worse — re-implementing the policy in TypeScript creates two authorities that can disagree, and deferring the check to completion lets a client upload gigabytes before being told no. The savepoint rollback takes the usage trigger's effect with it, asserted on both the object row and the project's usage total. | P6e |
| D-401 | The presigned upload cap is a **signed `content-length`**, not the doc's `content-length-range` | A `content-length-range` is a POST-policy construct belonging to a browser form POST, which is a different upload shape from a presigned PUT. Signing the exact length is the stronger equivalent: the client must send precisely what was signed or the signature fails, so a URL issued for 200 MB cannot be reused to push 2 GB. `content-type` is signed alongside it so a leaked URL cannot be repurposed for a different file shape. `UNSIGNED-PAYLOAD` is unavoidable — the bytes do not exist when the URL is signed — which is exactly why completion re-reads the true size and etag from the store instead of believing the client. | P6e |
| D-402 | Completion verifies the object's size against the intent even though the signed `content-length` should make a mismatch impossible, and sniffs content via a **ranged** read | An impossible state reached anyway means the assumption was wrong, and finalising on it would write a false number into the customer's quota. The content sniff (D-123) can only happen here, because no earlier moment had bytes to inspect; it reads the first 512 bytes rather than the object, since every signature lives in the first twelve and fetching a 4 GB video to see its header would reintroduce the bandwidth cost the presigned path exists to avoid. A refusal deletes the object immediately rather than deferring to the sweep, because the service knows *now* that the bytes are unwanted. | P6e |

2. Add the row here with the next free `D-xxx`.
3. If it overturns an existing decision, mark the old row **Superseded by D-yyy** — never delete rows.
