1 · The policy everything below obeys

Applied by scripts/storage-demo.sh over the project's own DATABASE_URL. There is no other permission system — RLS on storage.objects is the file ACL, so these six lines decide every success and every refusal on this page. 

create policy "avatars are readable by signed-in users"
  on storage.objects for select to authenticated
  using (bucket_id = storage.bucket_id('avatars'));

create policy "users manage their own avatar folder"
  on storage.objects for all to authenticated
  using (bucket_id = storage.bucket_id('avatars')
         and storage.prefix_owner(name) = auth.uid()::text)
  with check (bucket_id = storage.bucket_id('avatars')
              and storage.prefix_owner(name) = auth.uid()::text);

prefix_owner is the first path segment, so avatars/<uid>/photo.png belongs to that uid. Reads are deliberately wider than writes: any signed-in user may look at any avatar, and only the owner may replace one.

3 · Upload your own avatar

The bytes go to POST /storage/v1/object/avatars/<your uid>/photo.png — proxied through the service, which counts them, checks the declared type against the actual bytes, and writes the object before the row.

4 · Try to write into the other user's folder

The same request, one path segment different. WITH CHECK is what refuses it — a policy written with USING alone would filter reads and let this write land.

6 · A signed URL, and watching it expire

    

      Avatars are in a private bucket, so sharing one means minting a
      capability. This asks for a five-second URL so the expiry is watchable.
    

    

      A signed URL cannot be revoked before it expires — there is no
      per-URL kill switch, because a denylist check would put a database hop on
      the hottest read path. That is why the default is one hour, the maximum is
      seven days, and the documented advice for revocable access is to keep the
      bucket private and let clients fetch through the RLS-checked endpoint.
